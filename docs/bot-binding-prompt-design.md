# Bot-binding-aware pairing prompts — design

> **Status (2026-08-18):** design doc, not yet shipped. Plugin
> `bot_binding_prompts` is referenced but not yet implemented.

This doc designs the **user-facing text** that hermes-agent sends
to a user who has just DMed the bot but is not yet in
`bot-binding.db`. The current copy is hardcoded English in
`gateway/run.py` (lines 10108-10114) and is unhelpful for the
flopworld operator's user base (mostly Chinese-speaking; all users
are in a 4-tier system).

## 1. Why current copy is bad

Current text:

```
Hi~ I don't recognize you yet!

Here's your pairing code: `ABC123`

Ask the bot owner to run:
`hermes pairing approve <platform> ABC123`
```

Problems:

1. **Doesn't explain the system.** A new user has no context: who
   runs the bot, why they need approval, how long it'll take.
2. **Doesn't mention bot-binding.db.** The operator's preferred
   source of truth (bot-binding.db) is invisible; the user might
   wonder why "pair" is needed when "database lookup" would suffice.
3. **Doesn't localize.** flopworld's users are mostly Chinese.
   English copy with "Hi~" tildes is cute but condescending.
4. **Doesn't set expectations.** No mention of rate limits, no
   hint that repeated DMs will be ignored, no mention of which
   slash commands they could use after approval.
5. **Doesn't explain 4-tier.** flopworld uses
   `admin / power / vip / user`. A new user doesn't know which tier
   they'll land in or what each tier can do.
6. **No "where to ask" path.** User has no way to escalate if
   approval never comes.

## 2. Design goals

The new pairing copy should:

- **Be bilingual** (zh + en side-by-side, or pick one based on
  platform / locale).
- **Mention bot-binding.db** by name and explain that's where the
  operator adds new users.
- **Set rate-limit expectations**: "you'll get one of these per
  hour; if you don't hear back, ask the operator directly."
- **Provide escalation path**: a contact email / Discord handle /
  Telegram bot for the operator.
- **Explain tiers in one line**: "the operator decides your tier
  (admin / power / vip / user) when approving you."
- **Use a calmer tone**: drop the "Hi~" tildes; flat, helpful
  English / 平实,清晰 中文.

## 3. The four prompt variants

The new copy needs to cover four scenarios — not just "new
user, send code":

### 3.1 Variant A — first DM, bot-binding.db not consulted
*Scenario:* user DMs bot, not in `bindings`, plugin not loaded
(env-var fallback). Pairing code generated by hermes default flow.

EN:

```
Welcome! This is a private AI gateway.

You're not in my operator's allowlist yet. To get approved:

1. Send the operator this pairing code: `ABC123`
2. They run: `hermes pairing approve telegram ABC123`
3. You'll get full access on your next message.

If you don't hear back within an hour, ping the operator directly:
📧 theoperator@example.com
```

ZH:

```
欢迎！这是私人 AI 网关。

你还没被管理员加入白名单。要获得访问权限：

1. 把这个配对码发给管理员：`ABC123`
2. 管理员运行：`hermes pairing approve telegram ABC123`
3. 下一次发消息时你就能正常使用了。

如果一小时内没回复，请直接联系管理员：
📧 theoperator@example.com
```

### 3.2 Variant B — first DM, bot_binding_auth plugin consulted
*Scenario:* `bot_binding_auth` plugin ran, returned `None` (user
not in `bindings`), but the env-var path also failed. Plugin
intercepts before pairing code is generated and tells the user
**why** they need bot-binding.db entry (not a pairing code).

EN:

```
Welcome! This is a private AI gateway.

The operator manages access via a small database
(`bot-binding.db`). You're not in it yet — that's why I don't
recognize you.

Ask the operator to add you by running:

  INSERT INTO user_meta (user_id, role) VALUES ('<your-user>', 'user');
  INSERT INTO bindings (platform_id, chat_id, user_id)
    VALUES ('telegram:hermes_bot', '<chat-id>', '<your-user>');

Or, if the operator prefers the pairing flow, ask them to run
`hermes pairing approve telegram <pairing-code>` after they enable
it.
```

ZH:

```
欢迎！这是私人 AI 网关。

管理员通过一个小数据库（`bot-binding.db`）来管理访问权限。
你目前还没在里面——所以我不认识你。

请管理员把你加进去（执行）：

  INSERT INTO user_meta (user_id, role) VALUES ('<你的用户>', 'user');
  INSERT INTO bindings (platform_id, chat_id, user_id)
    VALUES ('telegram:hermes_bot', '<聊天ID>', '<你的用户>');

如果管理员更喜欢用配对流程，请他们执行
`hermes pairing approve telegram <配对码>`。
```

### 3.3 Variant C — rate-limited (already got code in last hour)

EN:

```
You recently requested a pairing code. Per policy I only send
one per hour — please wait before trying again.

If you haven't heard back, ping the operator directly:
📧 theoperator@example.com
```

ZH:

```
你刚请求过配对码。按策略，我每小时只发一个——请稍后再试。

如果还没收到回复，请直接联系管理员：
📧 theoperator@example.com
```

### 3.4 Variant D — locked out (too many failed approval attempts)

EN:

```
Your IP is temporarily locked out of pairing for {minutes} minutes
due to too many failed approval attempts.

This is automatic and not personal. If you genuinely need access,
contact the operator directly:
📧 theoperator@example.com
```

ZH:

```
由于多次失败尝试，你的 IP 被临时锁定配对功能 {minutes} 分钟。

这是自动触发的，与你无关。如果你真的需要访问权限，请直接联系管理员：
📧 theoperator@example.com
```

## 4. Tier explanation (for the welcome message)

Add a single line at the end of every welcome message:

EN:

```
Tiers: admin (full access) > power (everything except admin-only)
> vip (per-conversation + finance/fortune) > user (per-conversation only).
Your tier is set by the operator when they add you.
```

ZH:

```
权限等级：admin（全权限）> power（除管理员专属外）> vip（基础对话
+ 命理/金融）> user（仅基础对话）。你的等级由管理员设置。
```

## 5. Implementation plan

### 5.1 Minimal hermes-agent patch

Extend the `pre_gateway_dispatch` action handler (currently 4
actions: `skip` / `rewrite` / `allow` / `authorized`) with a 5th:

```python
if _action == "send_message":
    # Plugin wants to send a custom reply instead of letting the
    # default pairing flow run. Plugin must have already generated
    # any pairing code via pairing_store. We just send and return None.
    _text = _result.get("text")
    if isinstance(_text, str) and _text:
        _adapter = self._adapter_for_source(source)
        if _adapter:
            await _adapter.send(source.chat_id, _text)
            logger.info(
                "pre_gateway_dispatch sent custom message: platform=%s chat=%s",
                source.platform.value if source.platform else "unknown",
                source.chat_id or "unknown",
            )
    return None
```

Inserted into the existing `_action` chain. ~12 lines total
including the existing action branches. **Same size category as
the `authorized` action patch already shipped.**

### 5.2 Plugin: `bot_binding_prompts`

Lives at `~/.hermes/plugins/bot_binding_prompts/__init__.py`.

Logic:
1. On `pre_gateway_dispatch`:
   - If `event.source` looks like a DM (chat_type="dm")
   - And user is NOT in `bot-binding.db` (delegate to a helper that
     reuses `bot_binding_auth._lookup_user`)
   - And we're about to hit the pairing fallback (i.e. `_is_user_authorized`
     would fail), return `{"action": "send_message", "text": <welcome copy>}`
   - Else return None (don't interfere with normal flow).
2. The text is built from `agent.i18n.t()` with the right language
   resolution (zh / en). Falls back to en if no locale matched.
3. Rate limit / lockout variants use the existing
   `pairing_store._is_rate_limited` / `_is_locked_out` helpers — same
   policy as core, but with our better copy.

The plugin is a **sibling** to `bot_binding_auth`; they share a
helper module (or just duplicate the 8-line DB lookup).

### 5.3 Why a plugin (not a core change)

The string formatting is **policy** (how the operator wants to
greet their users). It varies per install. A plugin makes it
operator-local:

- One operator wants bilingual copy.
- Another wants strict no-emoji English.
- A third wants a `bot-binding.db` insert snippet inline.

A plugin lets each operator tune without forking hermes-agent.

### 5.4 Locale catalog

Add to `~/.hermes/locales/<lang>.yaml` (operator-local) or
hermes-agent's `locales/<lang>.yaml` (shipped default):

```yaml
gateway:
  pairing:
    unrecognized: |
      Welcome! This is a private AI gateway.
      You're not in my operator's allowlist yet...
    rate_limited: |
      You recently requested a pairing code...
    locked_out: |
      Your IP is temporarily locked out of pairing for {minutes} minutes...
    tier_explainer: |
      Tiers: admin > power > vip > user. Your tier is set by the operator.
```

If the operator doesn't ship locales for their preferred language,
the plugin's hardcoded fallback (in plugin source) is used. This
keeps the plugin standalone.

## 6. Anti-patterns to avoid

- **Don't leak operator email/Discord handle in the plugin.**
  Make it a config knob (`PROMOTED_OPERATOR_CONTACT` env var) so the
  operator sets their own contact info.
- **Don't include the pairing code in a generic welcome message.**
  Codes expire; if the welcome is replayed (logs, screenshots) the
  code leaks.
- **Don't promise response time.** "Within an hour" is a soft
  expectation; "within 5 minutes" sets the operator up for late-night
  Discord DMs.
- **Don't include `INSERT INTO bot-binding.db` SQL in the public
  copy.** It's an internal schema. The operator can give it
  separately if a user is technical, but the default message should
  not assume DB literacy.

## 7. Verification

Static test that the plugin's hook returns the expected action:

```python
import importlib.util, pathlib
spec = importlib.util.spec_from_file_location(
    "bot_binding_prompts",
    pathlib.Path("~/.hermes/plugins/bot_binding_prompts/__init__.py"),
)
mod = importlib.util.module_from_spec(spec)
spec.loader.exec_module(mod)

from hermes_cli.plugins import PluginManager, PluginContext, PluginManifest
pm = PluginManager()
manifest = PluginManifest(name="bot_binding_prompts", version="0.1.0",
                          source="user", key="bot_binding_prompts")
ctx = PluginContext(manifest, pm)
mod.register(ctx)
assert pm.has_hook("pre_gateway_dispatch")

# Simulate an unauthorized DM
class FakeSource:
    def __init__(self, platform, chat_id, user_id):
        self.platform = platform
        self.chat_id = chat_id
        self.user_id = user_id

from gateway.config import Platform
src = FakeSource(Platform.DISCORD, "9999999999", "9999999999")
class FakeEvent:
    def __init__(self, source):
        self.source = source

res = pm.invoke_hook("pre_gateway_dispatch", event=FakeEvent(src),
                     gateway=None, session_store=None)
assert res and res[0].get("action") == "send_message"
assert "Welcome" in res[0].get("text", "") or "欢迎" in res[0].get("text", "")
```

E2E: send a Discord DM from a `bot-binding.db`-absent user. The
gateway should:
1. NOT log "Unauthorized user" — it logs `pre_gateway_dispatch sent custom message`.
2. The user sees the bilingual welcome.
3. The next message (after the operator adds them) goes through normally.

## 8. Open questions

- Should `bot_binding_prompts` ship with the bilingual copy
  hardcoded, or read from a YAML the operator ships?
  **Recommendation:** hardcoded bilingual, operator-local override via
  `locales/<lang>.yaml`.
- Should it warn the operator (admin) via DM when an unknown user
  hits the welcome? **Recommendation:** yes, but rate-limited (once
  per user per day) and only if the operator is itself a known user
  in `bot-binding.db` with `role='admin'`.
- Should the welcome message include a unique-per-user link to
  a "request access" web form? **Out of scope for v1** — most installs
  don't run a web server.
