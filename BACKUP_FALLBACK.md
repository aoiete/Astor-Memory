# Backup / Disaster Recovery

What to do when astor-memory is broken beyond restart / watchdog.

## Scenario: bot-binding.db corrupt / lost

1. **Don't panic.** The DB is regenerable from `user_meta` rows + your
   own knowledge of which bots were bound to which users.

2. Re-initialize the runtime (this clears all data):

   ```bash
   am init
   ```

3. Re-bind the bots:

   ```bash
   am bot add-user --user-id=<id> --role=user --plan=<plan>
   am bot bind --platform=telegram --account-id=<bot_id> \\
       --chat-id=<chat_id> --user-id=<id>
   ```

   `bot-binding.db` is the **only** DB that has cross-tier state
   (platform + user + binding rows); the rest is per-tier and can be
   regenerated by re-running ingest.

## Scenario: source-tier rules lost

`source/memory/astor_bus_source.db` holds admin's R-class rules. If
lost:

1. Restore from backup (see operator runbook backup section).
2. If no backup exists, the R-classes will be regenerated as the
   agent encounters them — but it takes days/weeks. Critical ones
   (R218, R252, R380) should be re-loaded manually via `am write`.

## Scenario: per-user private data lost

**Cannot recover** unless user has a manual backup. astor doesn't
ship private DBs to any cloud by default. Tell the user — private
tier is per-machine, not per-cloud.

## Backup best practices

- **Cadence**: weekly (matches smart_backup.py) — sufficient for most operators
- **Retention**: keep last 3 backups; older backups can be archived locally
- **Pre-backup health check**: refuse if any DB fails `sqlite3 .integrity_check`
- **Scope**: include `bot-binding.db`, `admin.lock`, all tier DBs (bus/forge/nest × public/source/private_<user>), audit DB, lex DBs

```bash
# Sample backup script (run weekly)
for db in $(find ~/.astor -name "*.db"); do
    sqlite3 "$db" "PRAGMA integrity_check" | grep -q ok || {
        echo "INTEGRITY FAIL: $db"; exit 1;
    }
    sqlite3 "$db" ".backup /backup/$(basename $db).$(date +%Y%m%d)"
done
```

## Restoring from backup

```bash
# Stop the server first
am server stop
# Restore
cp /backup/astor_bus_public.db.* ~/.astor/public/memory/astor_bus_public.db
# Restart
am server start
```

The watchdog will pick up the server when it comes back.

## Scenario: complete machine loss

If you have a GitHub-mirrored copy of source code, you can re-install
on a new machine:

```bash
git clone https://github.com/<owner>/Astor-Memory
cd Astor-Memory
pip install -e .
am init
# restore backups
```

You will lose **all runtime data** unless you also backed up the runtime
DBs (not just source code). Source code alone is not enough.
